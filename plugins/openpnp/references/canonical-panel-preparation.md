# Prepare a canonical panel and save its library

Use this example when the request includes **preparing a new panel job** in the isolated native simulator. Preparation replaces the loaded job. Backing up an existing configuration still starts from its own saved boards/panels; the export tool does not author panels. The bundled `pnp-test` sample has flat board roots and is not a panel-creation example.

## Minimal input and existing Part binding

Start from [canonical-panel.json](../assets/examples/canonical-panel.json). It defines one 30 × 20 mm Board with one placement, one 70 × 20 mm Panel with direct board children `A` and `B`, and one root panel instance `P1`. The human-readable placement paths are `P1⇒A⇒R1` and `P1⇒B⇒R1`. Native editor requests use separate holder and placement selectors (`holder_instance_id: "P1⇒A"`, `placement_id: "R1"`); the canonical flattened `placementKey` is the JSON string `["P1","A","R1"]`. Preparation performs zero placements.

1. Read `openpnp_get_capabilities`, `openpnp_get_status` and `openpnp_get_configuration`. Require `bridge.simulator_profile: "native-simulator"`, an idle disabled machine with empty nozzles, and `bridge.canonical_part_bindings.profile: "existing-parts-v1"`. For later panel export, also require `bridge.portable_configuration.panel_library.profile: "saved-board-child-panel-library-v1"` and `archive_version: 3`.
2. Choose an **existing native Part** from `configuration.parts` for this preparation example (the stock simulator normally contains `R0805-1K`). Copy its exact `package_id` and positive `height_mm` into both `parts[0].packageId` / `heightMm` and `boards[0].placements[0].packageId` / `heightMm`. The file's `R0805` / `0.5` values are example data, not permission to create or change a native Part. Keep source ID `DEMO_R` and bind it explicitly to the observed native Part ID. For real user designs, choose the intended component rather than inferring equivalence from its name.
3. Preserve the full example structure. Canonical input uses `schemaVersion: 1`, `units: "mm"`, `coordinateConvention: "openpnp-top-view"`, and the `parts`, `boards`, `panels`, `instances` arrays. Every placement has `ref`, `partId`, `packageId`, `heightMm`, `x`, `y`, `z`, `rotation`, lowercase `side`, Boolean `enabled`, and `type: "placement"` or `"fiducial"`. Every instance/child has `id`, `kind`, `definitionId` and all four pose numbers, lowercase side and Boolean enabled. Panel/Board dimensions are positive millimeters; child poses are parent-local, placement poses board-local, root poses machine-frame, and angles are degrees. IDs in this native import use 1–128 ASCII letters/digits or `_.:+-`. Use distinct sibling IDs and exact definition references. Do not add pseudo-placement or panel-own-placement fields to this example: this canonical preparation route does not author them.

The two children reference one Board definition; repeating a canonical Panel definition at multiple root instances creates distinct native Panel definitions. Do not infer shared native Panel identity from a repeated canonical definition ID. The portable profile accepts only direct board children, even though the general canonical importer can represent nested panels.

## Public tool sequence

All mutating native calls below carry the active `session_id` and a **new lowercase UUID** `request_id`. Follow each returned `operation_id` until terminal, then wait for `native_busy: false` before the next mutation. On an unknown outcome, retain the original IDs and inspect/reconcile them without resubmitting the action. No enable, home, board-load confirmation or job start is needed to prepare/save/export this unused design.

1. Acquire the simulator lease with `openpnp_request_control_session`. Call `openpnp_import_job` with `format: "canonical-json"` and `content` containing the **entire adjusted JSON file as a string**. `revision` is calculated by the importer; do not invent one. Read the returned local SHA-256 `artifact_id` with `openpnp_get_artifact`, then `openpnp_validate_imported_job` with `mode: "offline"`. Expect two enabled expanded placements and no import errors. Offline checks do not establish production readiness.
2. Re-read the current `config_revision`. Call `openpnp_prepare_job` with the imported `artifact_id`, `expected_config_revision`, and `part_bindings: [{"source_part_id":"DEMO_R","native_part_id":"<observed Part ID>"}]`, plus session/request IDs. Omit `sample`. The existing-parts branch creates no Parts and requires matching native package/height. Observe success, `requested: 2`, `placed: 0`, and `part_library_changed: false`. Retrieve `result.part_resolution.artifact_id` with `openpnp_get_native_artifact` and retain its source/native mapping and hash.
3. Call `openpnp_save_job`. Retain **`result.artifact.artifact_id`**, the native document UUID and its SHA-256; download its ZIP with `openpnp_get_native_artifact` if a local copy is requested. This is distinct from the imported canonical SHA-256 artifact.
4. Call `openpnp_load_job` with that **saved native document artifact ID**. Native reload resolves and registers the saved Board/Panel definitions in this simulator configuration. Preparing or saving alone is not this complete saved-library setup sequence. Observe the new job ID and retained zero placed count, and read `openpnp_get_board_loads`; the roots still describe `P1` with descendants `A` and `B`. Reload invalidates execution/load confirmation; preserve that state while preparing the backup.
5. For the requested panel backup, continue with [portable export/adoption](portable-simulator-adoption.md). Read the latest revision before `openpnp_export_portable_configuration`. This example should produce version 3 with one panel, two children, zero own panel placements/pseudos, and two expanded board placements. Verify the manifest and archive hashes. Adoption occurs in a separate JVM and first launch uses a new operational state; the resulting simulator starts without the source job/history/lease.

This example supplies a saved design prerequisite, not a general panel-library CRUD tool or a physical panel-clearance check. It adds no measured fiducial registration, feeder stock assertion, inspection or execution authority. Native model validation, future board-load/material setup and any separately requested production run remain separate workflows.
