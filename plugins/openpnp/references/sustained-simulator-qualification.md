# Sustained simulator qualification recipe

The `sustained-workload` fixture is an isolated native OpenPnP simulation with finite virtual tray supply. It is distinct from the default `native-simulator` profile and from a physical machine. A full candidate uses a fresh absent job, exactly 10,000 unconsumed slots for the observed R0603-1K/R0603 identity, and a supplied 100-by-100 ordered grid with 1.5 mm pitch on a 150 mm board. It never resets feed counts to manufacture capacity.

## Native job order

For this ordered grid, the sustained fixture selects the public native `ReferencePnpJobProcessor.JobOrderHint.Unsorted` setting. Full-soak admission requires `get_capabilities.native_job_order: "Unsorted"` and the same value in `simulator_attestation.native_job_order`. Through MCP these fields are under the returned `bridge` object. The native bridge obtains the value from the actual processor and checks sustained-profile order during mutation admission. Read `job_order_rationale` as recipe provenance, not a client-provided permission.

The ordinary default fixture retains native `NozzleTips` ordering. Earlier sustained builds also used `NozzleTips`; the first 10,000-placement candidate exposed costly repeated ordering of remaining placements and was cooperatively interrupted. Preserve that incomplete result and its original recipe. An absent order field in earlier smoke evidence means it did not demonstrate this new admission requirement. Do not relabel historical evidence or infer a successful full soak from a short smoke.

`Unsorted` changes placement ordering for this fixture. Native job processing, planner/tool selection, vision, finite feeders, machine steps, and durable execution remain active. It does not replace the processor with a loop that increments counters. The native [job processor source](https://github.com/openpnp/openpnp/blob/5bd404cfc70f34103a3ca0fbb6b50c2b465f407c/src/main/java/org/openpnp/machine/reference/ReferencePnpJobProcessor.java) defines these public ordering choices.

## Evidence and boundaries

Full admission additionally requires the pinned loaded bridge JAR hash to match the verified local package, a measured idle native executor, a JVM maximum heap of at most 2 GiB, and the advertised aggregate artifact storage limit. The runner executes a hashed private copy of the complete MCP directory and verifies that copy afterward. Preserve the initial recipe, progress snapshots, native feed counts, resource samples, event-overflow resynchronization snapshots, completion/failure report, and any operator interruption.

A completed short or reduced-count run remains smoke evidence. The eight-hour/10,000-placement simulator result, independent placement-cycle overhead comparison, and physical machine qualification are separate claims. A native capacity or persistence failure must remain a failed/unqualified result; do not delete artifacts, weaken durability, reset material, or replay uncertain actions to reach a target. Skills must inspect the installed capability and name the missing prerequisite if this fixture recipe is unavailable.

## Bounded polling and final receipts

Use `view: "progress"` for periodic `get_status` and active-job `get_operation` reads. Progress returns native resource counters and cached feeder observations without archiving the full response. `machine.snapshot_at` describes the feeder snapshot; `job_progress.observed_at` and `through_sequence` describe the job counts. These timestamps have separate sources and do not establish an active lease. A null resource value means unavailable, including journal size after a journal failure.

Feeder progress includes at most 16 rows and 8 KiB, with `feeders_count` and `feeders_complete`. The sustained runner requires `feeders_complete: true` before aggregating supply; a partial list cannot establish remaining stock. Preserve native IDs, counts, timestamps, faults, and unknown outcomes. Progress is a selected observation, not a retained full snapshot.

The runner saves the bounded job disposition and attempts one exact full receipt for each observed terminal or cleanup-paused disposition. A failed detail read preserves the known operation/request IDs and state and records the storage/transport error; it never repeats the native action. Initial/baseline reads, event-resync configuration snapshots, and selected final/artifact evidence remain explicit full reads. Evidence capacity is finite with no eviction; this polling change does not provide unlimited retention or qualify an eight-hour run by itself.

## Event cadence for the eight-hour recipe

The harness accepts `--event-poll-seconds 60..600`, with 60 seconds retained as its default. The reviewed eight-hour recipe explicitly selects `--event-poll-seconds 600` to bound retained event/resynchronization responses. This leaves ten-second status samples, one-second active-job progress and sixty-second lease renewal unchanged. A forced post-job event read remains immediate. The final report records the selected cadence.

For the single-job recipe, at most 50 event opportunities plus 32 setup/disposition allowances use 82 of the 128 response-file slots. Each event poll returns either an event page or a resynchronization marker followed by one configuration read. This file-count calculation does not prove the separate byte budget: large terminal/event receipts, journal growth and PNG sizes require their own measurements. Preserve any limit failure; no archive eviction or capacity increase is part of this recipe. A short smoke and these calculations do not qualify eight hours.

## Independent timing qualification

Preserve the original report and inspect its separate `independent_timing_gate` and `continuous_simulator_soak_qualified` fields. The older `simulator_soak_complete` field uses the harness elapsed timer; it is insufficient for continuous-duration qualification. A running report is always incomplete. After a run, the read-only `scripts/openpnp-soak-timing.mjs --report REPORT_JSON --progress PROGRESS_JSONL --output NEW_JSON` command creates a separate assessment and never overwrites the raw report. A full run exits successfully only when the independent gate passes; smoke exit behavior stays unchanged. The standalone assessment exits after writing its result, so read its qualification field.

The predeclared timing policy requires a successful original result, stable bridge UUID and observed JVM PID/start-time identity, at least eight hours between native timer observations inside the workload window, consistent harness/wall/native clocks, and no observation gap over 60 seconds. This gap budget covers the declared ten-second cadence and bounded observation calls; it is not chosen from the run's outcome. Cross-clock divergence and native-read duration are each bounded at 30 seconds (the 25-second status-call and five-second process-observation budgets). First and last observations must cover both workload boundaries within the same 60-second budget.

Every sample is checked for clock order and bridge/JVM identity before workload filtering, including samples outside the selected window and samples with invalid native-read bounds. A backwards window transition permanently fails the gate. Prefix/suffix observations cannot contribute native duration. Closed-file assessment also requires matching initial/final progress records and report identity. PID-to-endpoint association remains caller-provided; these checks do not add process attestation.

New samples bracket the native read with harness timestamps. Historical samples lacking those bounds remain diagnostic evidence and cannot retroactively prove a precise workload-only duration. Native elapsed spans use differences, excluding JVM startup time. For a future fresh qualification run, explicitly select `--duration-hours 8.1` (8 hours 6 minutes) to allow for the baseline reads before the first workload sample and endpoint coverage. This is a planned workload duration, not a guarantee of qualification: the measured native span must still reach eight hours and every timing check must pass. The default remains 8 hours. A declared run may finish without eight full observed native hours when endpoint coverage is short; the result then stays timing-unqualified. Do not extend a live frozen run, restart it, relax the policy, or replay work to obtain a pass.

Clock divergence or a sampling gap does not determine its cause. Do not infer operating-system suspension, continuous CPU execution or physical operation from these timers. Preserve completed placement/feed records and wall-time evidence separately, including when the timing gate is unqualified. This timing gate does not establish full A11, independent placement inspection, placement-cycle overhead or hardware qualification.
