# Bounded native Codex driver

`scripts/native_codex.py` services one exact pending native handoff with a real
local `codex exec --json --ephemeral` process. It does not install a plugin, choose
another model, accept a supplied execution trace, advance the factory journal,
deliver a patch, or issue runtime-native authority. The trusted lifecycle caller
must invoke the driver directly and then use `RunJournal.accept_native` with an
independent deterministic artifact validator.

The primary supported protocol target is **codex-cli 0.167.0-alpha.3.2**.
The retained **codex-cli 0.164.0-alpha.11.1** protocol uses the same strict
managed startup check, but newer managed settings can make that client reject
startup. Select and pin a compatible executable explicitly; unsupported managed
fields stop the run before a model call. The explicit older
**codex-cli 0.144.3** branch remains available, but its local configuration
preflight does not qualify managed cloud compatibility; a newer managed field
can make its subsequent `exec` startup fail before a model call. There is no
automatic client substitution or managed-policy bypass. Local source was also
inspected for native skill mentions, plugin selection, exec approvals, and JSON events.
Controlled subprocess tests are not an actual model or installed-plugin
qualification. The candidate still requires separately authorized native smoke
and repeated behavior checks before release.

## Explicit invocation

Use the installed dependency environment and an exact model selected by the
operator. Values below are placeholders; a digest or model is never defaulted.

```sh
python /installed/devsecops/scripts/native_codex.py \
  --request /owned/run/native/review/request.json \
  --request-sha256 REQUEST_SHA256 \
  --run-root /owned/run \
  --installed-root /actual/codex-home/plugins/cache/MARKETPLACE/devsecops/VERSION \
  --package-sha256 SHA256_OF_INSTALLED_SHA256SUMS \
  --plugin-id devsecops@MARKETPLACE \
  --codex /absolute/path/to/codex \
  --engine-python /approved/external/venv/bin/python \
  --client-version 'codex-cli 0.167.0-alpha.3.2' \
  --model EXACT_OPERATOR_SELECTED_MODEL \
  --reasoning-effort EXACT_OPERATOR_SELECTED_EFFORT \
  --output /owned/native-execution-NEW \
  --total-timeout 900
```

The Python API is `execute_native_codex(request_path, *, run_root,
request_sha256, installed_root, package_sha256, plugin_id, model,
reasoning_effort, engine_python, expected_client_version, executable, output, total_timeout=900,
max_trace_bytes=16000000, cancel=None)`. `cancel` may be a `threading.Event`.
The evidence directory must be new and outside the child writable directory.
For the current macOS app bundle, select
`/Applications/ChatGPT (Alpha).app/Contents/Resources/codex-cli/CodexCLI.app/Contents/MacOS/codex`
as the executable. Its neighboring `bin/codex` is a shell launcher; selecting the
Mach-O executable makes the recorded hash identify the actual CLI binary.
App updates can change that binary, so recheck its exact version and identity
before qualification.

The standard request must validate against `native-request.schema.json`. The four
allowed handoff workflows are review, diagnosis, correction, and recovery. All six
run identities remain in the exact hashed request. Requests must be current, their
input files must match their byte lengths and SHA-256 digests, and artifact paths
must be normalized relative paths inside the owned run without symlinks.

The native registry is queried directly with `codex plugin list --json`. The exact
plugin must already be installed and enabled. The driver resolves its actual
versioned installation under the existing `CODEX_HOME` (or normal `HOME/.codex`),
verifies `SHA256SUMS` itself against the supplied package identity, and checks every
listed file plus exact file membership. Missing manifests, extra files, links,
unknown version, missing workflow, disabled installation, or package drift stop
before the model invocation. The original v0.1 installation without `SHA256SUMS`
cannot satisfy this gate. A source checkout or extracted archive is not an
installation. Dependency environments belong outside the immutable package;
the shell receives `PYTHONDONTWRITEBYTECODE=1` to avoid generated bytecode there.

`--engine-python` is required. The driver executes that exact absolute interpreter
path with isolated Python startup and bytecode disabled, checks Python 3.11 or
newer and the pinned `jsonschema==4.25.1`, `PyYAML==6.0.3`, and
`zstandard==0.25.0` imports, and records
the reported executable/prefix/base prefix, import versions and entry-module
hashes. It separately hashes the resolved executable and `pyvenv.cfg`, when
present, and binds the supplied symlink target. It repeats this check after the
native run. Execution preserves the supplied venv `bin/python` path; invoking its
resolved base executable would incorrectly discard the venv. This verifies the
selected local interpreter and required imports, not every transitive Python
module's provenance. The native prompt supplies that interpreter and the exact
installed Python wrapper, and forbids dependency installation or `uv run` that
would attempt to modify the immutable plugin cache.

## Native execution and policy

The prompt uses Codex's exact native mention syntax:
`[$workflow](/actual/installed/plugin/skills/workflow/SKILL.md)`. It includes the
bounded request and exact request hash, not a copy of skill instructions or a
known-good answer. The child is told to use only that workflow and return the
native result as its final JSON message. It writes artifacts only in the request's
empty private `output_directory`. The driver validates and exclusively publishes
the exact final-message bytes at `result_path`; the child needs no write access to
the request or journal.

The handoff status describes artifact production. A completed workflow has an
empty handoff `gaps` array even when its report correctly says `fail` or `unknown`.
Those findings and evidence gaps remain in the report and explanation. An engine
exit code of 1 or 2 may still produce a valid report; a missing or invalid required
artifact makes the handoff incomplete. The driver validates this distinction
against the full result schema and never changes the report's decision.

The fixed command uses `--json --ephemeral --strict-config --model EXACT
--sandbox workspace-write --cd OUTPUT_DIRECTORY --skip-git-repo-check --color
never --output-schema FROZEN_RESULT_SHAPE`. The flat structured-output shape is
derived from the installed result schema and retained privately. Conditional
completion rules are still enforced by the full trusted handoff validator.
There is no `--add-dir`, `--ignore-rules`, `--ignore-user-config`, bypass
flag, alternate provider, fallback model, or recursive factory invocation.
User configuration, managed requirements, execpolicy rules, and existing approval
and safety hooks remain loaded. Headless Codex normally denies escalation, and
its existing managed AutoReview behavior remains the CLI's responsibility. The
driver does not create approval rules or retry with broader permissions.

Before any model invocation, the primary client loads the same overrides through
`app-server --strict-config --print-startup-config`. This documented command
validates local and managed startup configuration without starting the app
server. No MCP request, conversation, model call, or tool call is sent. The exact
response is retained privately as `startup-config.json`; its byte hash and
reported app-server version are checked and bound in the invocation evidence.
Configuration failures stop before the model and return a sanitized error.
The explicit 0.144.3 branch uses `mcp-server --strict-config` with stdin EOF and
labels its scope `local-config-only`; it cannot establish cloud compatibility.
Both branches preserve the configured managed baseline and policy. This checks
configuration compatibility, not model availability or native workflow success.
The entire preflight has an
independent 30-second cap, shortened by the remaining request deadline. Before
strict loading it checks the effective MCP inventory and rejects any enabled
server.

Per-process configuration disables tool-sandbox network access and extra `/tmp`
writable roots, unrelated installed plugins, every listed MCP server, apps,
connectors, browsers, multi-agent tooling, web search, automatic skill MCP
installation, skill environment prompting, memories, and Chronicle. Only
canonical feature names supported by the selected exact client are used. The
0.164.0 branch also disables `shell_snapshot_v2` and `step_model_switching`, which
0.144.3 does not expose. The target
plugin is never force-enabled. Only a skills-only package is supported. No
`HOME` or `CODEX_HOME` value is changed. The CLI inherits a small environment list
for paths, locale, TLS, and existing proxies; customer credentials and arbitrary
variables are not inherited. Existing Codex account authentication is used.
Shell inheritance is reduced and the existing `PATH` is passed explicitly.
`TMPDIR` points to the exact private output directory, so approved engine tools
can use temporary files without granting another writable location. Capability
names are encoded as TOML table keys because this client's dotted override
syntax does not parse quoted path segments. Disabled MCP entries include an
inert transport of the observed kind: `/usr/bin/false` for stdio or a loopback
placeholder for HTTP. This permits strict bootstrap validation even for servers
supplied later by cloud configuration. Original URLs, commands, headers, and
credentials are never copied; the entries always have `enabled=false`, and
unknown transport kinds fail closed.

These overlays narrow the configured capabilities, but they are not a new OS
security boundary. Existing managed policy and hooks still apply; process
environment filtering does not revoke filesystem credentials or guarantee that
every user config value is secret-free. Run qualification in an approved owned
workspace with appropriately scoped host access. This driver does not request
new service credentials or silently weaken a rejected policy. An actual MCP,
collaboration, or web-search event makes the result incomplete.

## Bounds and evidence

The total deadline covers preflight, process execution, post-verification, and
successful publication, and is capped by request expiry. The default is 900
seconds, with an allowed range of 1–3600. Stdout and stderr share one 16 MB bound
(configurable from 1 KB through 64 MB); every JSON event is bounded to 1 MB and a
trace to 20,000 events. Inputs/outputs retain the handoff's 16 MB per artifact and
64 MB aggregate limits. Installed content is capped at 4000 files and 128 MB.
Between `thread.started` and `turn.started`, the client may emit completed
`error` or `notice` items containing only an ID, type and diagnostic message.
These are retained privately in `startup-diagnostics.json` and bound by the
terminal manifest; the normalized receipt exposes only their count and file
identity. At most 32 diagnostics, 8 KB per message and 64 KB of diagnostic events
are accepted. This uses the event shape, never a warning-message allowlist.
Pre-turn tool activity, malformed sequences, top-level errors and `turn.failed`
remain failures. Diagnostics cannot replace the one completed turn or any result
and artifact validation, and managed configuration remains unchanged.
The UTC request window is rechecked immediately before and after result publication
and at terminal publication, so a clock adjustment cannot admit an expired request
merely because the monotonic process deadline has not elapsed.

The driver drains nonblocking pipes. On timeout, overflow, or cancellation it
sends SIGINT, gives Codex up to 500 ms to interrupt the turn and clean up managed
tools, then kills/reaps its process group. It also stops group members left after
normal completion. This bounded cleanup grace can extend elapsed time beyond the
execution deadline. Detached groups or daemons are not proven cleaned up;
`detached_descendant_cleanup` remains `unverified`. It retains actual partial trace
after a failed child. The wrapper treats SIGINT and SIGTERM as cancellation; an
abrupt host kill cannot be reported as success. Platform resources and pending
journal requests are not cleaned up by terminating this local process.

Private evidence includes the exact request and prompt, installed content manifest,
invocation/configuration, actual `trace.jsonl`, private stderr, exact native result,
and content-addressed copies of referenced artifacts. Files are mode 0600 in a
0700 directory, published through anchored directory descriptors. Terminal
`manifest.json` binds all file bytes. Output/result directory replacement or a
late terminal write withdraws terminal publication; partial private files may
remain for diagnosis. Existing files are never overwritten. Raw trace and stderr
may contain sensitive data and are never echoed by the wrapper. MCP inventory
bodies can contain inline credentials: only server identifiers are retained.

`execution.json` records only directly collected process/installation facts.
Client executable hash, requested model, package hash, request/result hashes,
thread ID, artifact identities, and trace hash are retained. Model-supplied extra
provenance fields are rejected by the result schema. The consumed JSON protocol does **not**
expose a provider-observed model, actual turn ID, or explicit skill-injection event;
these remain null/unobserved with explicit observability limits. The canonical
contract requires the configured model/client identity and an actual native trace;
these missing protocol fields are not additional canonical acceptance gates.
Independent skill-behavior/artifact validation is still required. This is deliberately
not a `runtime-native-execution` receipt. `runtime_native_authority` remains
`not-issued`, and scenario assertions remain `not_evaluated`. A future trusted
host adapter must collect any missing authority directly; JSON conversion cannot
provide it.

Exit 0 means the process and complete artifact handoff were observed and checked.
It does not certify the skill's reasoning, a deployment, or the demo. Exit 2 means
setup/execution/artifact handling is incomplete; exit 130 means observed local
cancellation. A valid model-produced `incomplete` result is retained for journal
handling without being upgraded to success.

## Fifth skill component exercise

The factory skill cannot appear in a normal handoff because that would recurse
into the orchestrator. A separate component request may use the same bounded
request shape with `workflow: run-software-factory-demo`,
`required_artifact_kind: explanation`, `qualification_mode:
factory-doctor-component`, and an explicit supported `profile`. Its only input
artifact names are required `factory-config` and optional `factory-lock`.

That mode asks the native skill to run only the installed `factory_demo.py doctor`
and retain its actual stdout and an explanation. It does not run `e2e`, generate
credentials, or provision anything. Its receipt permanently says
`factory-doctor-component` and `canonical-factory-demo-not-exercised`. Successful
doctor behavior is useful component evidence, never fifth-skill canonical demo
qualification. The canonical scenario still requires the complete real lifecycle,
native correction, independent recovery, reset, and cleanup.
