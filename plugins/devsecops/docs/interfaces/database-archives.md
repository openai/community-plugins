# Grype database archive admission

The existing pinned Grype scanner accepts original gzip or Zstandard database archives. Format selection uses the actual magic bytes. The copied local import path has the matching fixed `.tar.gz` or `.tar.zst` suffix; source filenames and URLs never become native tool arguments.

The Zstandard path uses the pinned `zstandard==0.25.0` dependency on Python 3.11 and later. It streams decoded bytes into a private temporary tar file inside the scanner scratch directory, validates that the sole member is a regular `vulnerability.db` with a SQLite header, and removes the temporary file on exit. No archive member is extracted to a filesystem path by this validator. Grype then imports the original hash-checked compressed archive.

The validator bounds compressed bytes to 1 GB, decoded tar bytes to 3.01 GB, the SQLite member to 3 GB, decoder windows to 128 MiB, frames to 16, blocks to 65,536, and each I/O chunk to 64 KiB. The window budget is decoder working memory in addition to interpreter, native scanner and I/O overhead. All loops use the scan's existing absolute deadline. Tar metadata retains the existing 64 KB per-header, 8 MB cumulative and 16-level nesting limits. Provision enough scratch space for the original archive, temporary decoded tar, and Grype's imported database.

The original official package built 2026-10-27, SHA-256 `16a9163729d925edbf911db3542666748f06ddb2ce541211a4f1314349e20442`, advertises a 128 MiB window in its six-byte Zstandard header `28b52ffd0488`. Its first local admission attempt correctly stopped at the earlier 64 MiB cap before Grype import. The fixed 128 MiB cap admits that observed format; a 256 MiB declaration is rejected before allocating the decoder. Both the independent header check and the pinned native backend enforce a byte-based limit.

A structural frame pass rejects incomplete frames, dictionary dependencies, skippable frames, oversized blocks/windows and trailing compressed garbage before decoding. This is necessary because the pinned streaming reader can return EOF for a truncated frame. The decoder separately validates encoded blocks and optional checksums. Nonzero content after the tar's end marker is rejected; concatenated frames are supported only when their combined content is one admitted tar archive.

The scanner records the original compressed archive SHA-256, byte count and compression, together with Grype's actual database schema, build time and completion-time age. Archive validity and native import success establish mechanics and content integrity. They do not establish authentic database provenance or complete vulnerability coverage. The earlier official metadata GET returned HTTP 403. A later bounded request through the normal network route returned HTTP 200; the original listing and matching archive then passed native local import. A controlled older urllib3 image produced 10 findings, while missing distribution metadata remained an explicit coverage gap. This is genuine-database component evidence, not a qualified mission image or disconnected factory run.

Tests use real Zstandard frames and the actual pinned Grype executable against a deliberately synthetic database. They cover truncated/checksum-damaged frames, unknown decoded size, expansion/window/frame/block limits, malicious tar paths and trailing content, deadlines, gzip compatibility, and successful native Zstandard import. The synthetic scan remains unknown for genuine CVE coverage.
