## Why this driver

QEMU supports a full guest OS with TCG when hardware acceleration is absent. Its user-mode network backend runs without root, and explicit host forwarding can expose selected guest ports. TCG is software emulation; eight emulated CPUs do not establish the performance of eight hardware-assisted virtual CPUs. [QEMU system introduction](https://www.qemu.org/docs/master/system/introduction.html), [network backend documentation](https://www.qemu.org/docs/master/system/devices/net.html), [multithreaded TCG](https://www.qemu.org/docs/master/devel/multi-thread-tcg.html).

The full guest confines RKE2's root-level service, kernel/network configuration, container runtime, and CNI effects to a disposable Linux machine. RKE2 documents systemd-based Linux requirements and root/sudo installation. Guest OS/version support still must be checked against the exact selected RKE2 release. [RKE2 requirements](https://docs.rke2.io/install/requirements), [RKE2 installation](https://docs.rke2.io/install/quickstart).

| Alternative | Decision |
| --- | --- |
| Install RKE2 directly on the current devbox | Reject: changes the host's services and networking. |
| Privileged RKE2/systemd container on its existing Docker daemon | Do not use as the reference isolation boundary: shares the host kernel and requires privileges that need separate assessment. No vendor-qualified reference for this arrangement was established. |
| Big Bang evaluation quickstart | Useful separate evaluation route, but its documented cluster is k3d/k3s. It does not establish canonical RKE2 evidence. |
| Existing Mac/Colima | Excluded from this decision because of current pressure and existing workloads. |
| New cloud instance or hypervisor change | Not authorized by this investigation; a later option if TCG fails the measured gate. |

The official evaluation quickstart asks for an 8-CPU, 32-GB Ubuntu VM and Registry1 credentials, but also provisions k3d. It should not be run unmodified against this host. [Big Bang evaluation quickstart](https://docs-bigbang.dso.mil/3.34.0/docs/getting-started/quick-start/).

## Proposed resource and privilege boundary

Start with a bounded guest-boot experiment: 4 emulated CPUs, 8 GiB RAM, and a fresh 40-GiB sparse disk. If it passes, create a separate canonical candidate with **8 emulated CPUs, 32 GiB RAM, and a 160-GiB sparse disk**. These are proposed budgets, not established Big Bang minimums. Reserve at least 10 GiB of currently available host RAM and 150 GiB of physical free disk; enforce a host CPU budget and monitor physical disk growth. Do not run two canonical guests concurrently on this host.

Run QEMU as the existing unprivileged operator inside a disposable Docker container. Keep the image, seed, private QMP socket, logs, ownership record, and credentials in a dedicated operator-owned directory. Use a new guest machine identity and per-lab SSH key. No host disk passthrough, shared home directory, agent forwarding, Docker socket mount, TAP device, manually configured host bridge, or global DNS change is needed. Bind guest SSH/API forwards to host `127.0.0.1` on allocated high ports. Use an SSH tunnel for workstation access.

The implemented acquisition path resolves the official Ubuntu 24.04 container to its repository digest, then builds a disposable tool image using exact Ubuntu QEMU and cloud-image-utils package versions. Rootless apt fetches signed official Ubuntu metadata and packages into a private configuration, status, lists, and cache directory, with system apt hooks excluded. The Docker build then runs with `--network=none` using those package files. Runtime uses the immutable resulting image ID. All acquired package hashes, signed metadata hashes, the complete installed package inventory, and Dockerfile hash are retained; moving transitive apt dependencies mean the Dockerfile alone is not a bit-for-bit rebuild guarantee. No system-wide package is installed. Docker daemon access is privileged infrastructure already available to this operator; the guest process itself has no added capabilities or host device access. Guest bootstrap does need root/sudo for RKE2, guest networking, storage, and the lab's service accounts. Guest privilege does not authorize host privilege changes.

The probe container has a read-only root filesystem, all capabilities dropped, `no-new-privileges`, a 4-CPU quota, 9-GiB memory/swap ceiling, and a 256-process limit. The extra GiB covers QEMU overhead around the 8-GiB guest. Its only bind mount is the new private lab directory. A dedicated internal Docker network provides no external route; QEMU uses user-mode networking inside it. Only a loopback SSH publish is requested. Docker 29.7.2 on this host suppresses that publish on its internal network; the helper instead verifies the exact owned container/network identity and connects from the devbox to its private bridge address, with no effective host port publication. The seed helper uses no network and a separate 1-CPU/512-MiB limit. Cloud-init and SSH key material remain private.

The dated Ubuntu cloud image and SHA-256 are pinned in [lab_tcg_probe.py](../../scripts/lab_tcg_probe.py); checksum signatures must match the pinned Canonical cloud-image signing fingerprint before image content is accepted. SSH verifies a pre-generated per-run guest host key; first-connection trust is not inferred from `ssh-keyscan`.

Run the explicitly authorized probe from the repository root:

```sh
python3 scripts/lab_tcg_probe.py --host your-linux-lab --receipt work/v02/tcg-boot-probe-01.json
```

Every attempt needs a new receipt path. The helper always attempts cleanup of its exact recorded, ownership-checked containers and network. It retains the immutable tool image and private guest disks, keys, seed, logs, state, and provenance for diagnosis. A missing receipt requires reconciliation of the private state before a retry. This is an operator engineering helper, not the customer-facing factory-demo runner or a live readiness assertion.

For ingress, select an explicit guest-local NodePort/SNI mapping and private CA instead of assuming a cloud load balancer. Keep its DNS, canonical service URLs, runner callbacks, and browser access consistent before installing applications. Use dedicated trust configuration rather than disabling TLS verification. Store recoverable demo credentials privately; export only references/redacted metadata. Local demo accounts cannot substitute for authentic Registry1 authorization or image trust evidence.

## Retained-guest driver development slice

`src/devsecops/factory/tcg.py` implements an operator API for an already provisioned private disk: `RetainedTCGDriver(private_state_dir, spec).up(operation_id, deadline=...)`, `.reconcile(...)`, and `.down(...)`. The caller supplies a monotonic deadline, holds the lifecycle/environment mutation lock, and records its mutation intent before calling the driver. Each method returns a `TCGObservation` with observed state, an immutable receipt path and SHA-256, and the observed mutation effect. This is a low-level RKE2 foundation; it is not registered as a complete canonical Big Bang driver.

The spec binds scenario, assertion, exact package-manifest, lock, configuration and environment hashes, plus run/environment identities, provision ownership, the original CA, immutable tool image, remote private path, and an explicit SSH transport snapshot. Initial host-key provenance must come from an authenticated control plane or independent operator verification. The driver rejects TOFU, ambient SSH configuration/control masters, altered transport files, changed inputs, foreign/replaced Docker IDs, and unresolved create attempts. The transport uses the independently obtained server key and a private configuration; guest SSH separately uses its provisioned host key.

The SSH snapshot includes the issued client certificate and its derived public identity so `IdentitiesOnly yes` can select the matching signer in the explicitly named existing agent. No private agent key is exported. The first retained-transport check failed with an expired certificate and incomplete agent identity selection; that receipt remains recorded. After correcting public identity selection, a real read-only `true` command passed using the pinned server key and isolated configuration (`work/v02/tcg-pinned-ssh-check-03.json`). This is transport evidence only.

For short-lived credentials, `driver.renew_certificate(issued_certificate_path, operation_id, deadline=..., minimum_validity_seconds=...)` accepts a certificate already issued by the operator's normal helper. It accepts no issuance command or route override. It compares the complete client key, certificate type, key ID, principals, critical options, extensions, reserved field and issuer against the original owner; only nonce, serial, validity and signature may rotate. The caller must budget enough remaining validity for the next phase and cleanup. A real certificate-only `ssh true` against the original pinned host must succeed before an atomic active-generation update. Immutable generation receipts retain the previous certificate and audit linkage; a failed probe leaves the prior generation active. The original owner, source and six input hashes remain unchanged. Both renewal and later connections exclude raw-key/password authentication fallback. Unit tests include parsing a real OpenSSH-issued certificate; attempt 05 also records successful live generation activation under the frozen source.

Agents that advertise the issued certificate use the default `agent_protocol="native"`. An operator can explicitly bind `agent_protocol="certificate-view-v1"` when creating a new transport snapshot for an existing ECDSA P256 signer that advertises only its public key. The option changes the immutable transport identity; it cannot be enabled silently on a retained owner. OpenSSH's certificate-only algorithm filter otherwise removes that raw public identity before a separate `CertificateFile` can locate its agent signer. Secretive 4.0.0's native certificate-import path also has a reported Ed25519-CA parsing defect. [OpenSSH authentication selection](https://github.com/openssh/openssh-portable/blob/V_10_3_P1/sshconnect2.c), [Secretive certificate parsing issue](https://github.com/maxgoedjen/secretive/issues/841).

The optional view exposes one exact issued certificate through a temporary private socket for one SSH command. It accepts one signing attempt for the exact certificate, user, pinned host and session; only the outer agent key reference changes to the existing signer. The signed SSH payload remains unchanged. It rejects raw-key authentication, arbitrary signing, forwarding, agent mutation, a second signing attempt after an ambiguous result, and expired or late responses. One upstream connection preserves any native connection constraints; an unsupported session-binding extension remains unsupported. Pinned OpenSSH verifies the server signature and host key. The view additionally checks the signed payload's exact host/user/session/certificate bytes; it does not independently authenticate the extension's host signature.

Authentication has a 40-second absolute bound, bounded packets and a single frontend connection. The view closes after its signing attempt; context cleanup removes only its own socket and temporary config. Private `ssh-agent-*.json` receipts record counts, identities and cleanup without signed payloads or private keys. Renewal, remote actions and tunnel startup use the same context. Tunnel shutdown uses the recorded owned control socket with public-key authentication disabled, so it does not depend on a temporary configuration or a fresh signing request. Agents and other certificate algorithms outside this closed compatibility path remain on the native path; there is no automatic fallback.

The real read-only compatibility probe succeeded on 2026-10-28: `work/v02/tcg-certificate-adapter-probe-02.json` records certificate-only authentication against the pinned host, one host-bound signing attempt, a successful `true` command and removal of the temporary agent. The integrated frozen revision `5dbc0009616a0fa419abfba39221e3b04fea4dcc` subsequently activated a renewed generation and authenticated the owned guest during adoption attempt 05. Neither transport result establishes guest readiness or storage durability.

Namespace and node UIDs form the retained cluster fingerprint. `reconcile` reads the actual resources and API; a driver's saved JSON cannot establish current readiness. An absent resource after a disconnected create remains unknown. Observed partial deletion is recorded as partial and cannot establish cleanup success. A new mutation requires explicit reconciliation of a preceding unresolved operation.

A source/package/input change requires a newly reviewed environment ownership transition; this slice does not silently migrate an existing owner record. No automatic cleanup happens when the higher-level lifecycle yields `awaiting_native_step`/exit 3. Terminal cleanup remains the lifecycle caller's responsibility.
